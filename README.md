# CabFlow: Cab Booking Platform (Spring Boot + React)

A full-stack ride-hailing app. Riders book rides, drivers accept them, and the rider tracks the cab live.
Payments run in demo mode, receipts are generated as PDFs, and admins get a dashboard.

| | URL |
|---|---|
| **Live app** | https://cabflow-app-beta.vercel.app |
| **API** | https://cabflow-app.onrender.com |
| **API health** | https://cabflow-app.onrender.com/actuator/health |

> The API runs on a free Render instance that sleeps when idle, so the first request after a quiet period can take up to a minute.

## Tech stack

| Layer | Technology |
|---|---|
| Backend | Java 17, Spring Boot 3.5, Spring Security (JWT), JPA/Hibernate, Spring WebSocket (STOMP), Stripe Java SDK, iText (PDF), Maven |
| Frontend | React, TypeScript, Vite, Tailwind CSS, Leaflet, @stomp/stompjs |
| Database | PostgreSQL on Neon (serverless) |
| Hosting | Render (backend, Docker), Vercel (frontend), Neon (database) |

## Architecture

```
                         HTTPS (static site)
   Browser  ───────────────────────────────────►  Vercel   (React + Vite build)
      │
      │  HTTPS REST (Bearer JWT)
      ├──────────────────────────────────────────►  Render  (Spring Boot in Docker)  ──JDBC + SSL──►  Neon PostgreSQL
      │  WSS / STOMP (JWT in the CONNECT headers)      │                                              (ap-southeast-1)
      └──────────────────────────────────────────►─────┘
```

```
backend/    Spring Boot API: auth, rides, matching, WebSocket, payments, receipts, admin
frontend/   React single-page app (rider, driver and admin screens)
```

## Features

- **Auth:** register and log in as rider or driver, BCrypt passwords, JWT (60 min), role-based access
  (rider / driver / admin), rate limit on login and register, change password from the Account menu.
- **Booking:** fare estimate per cab tier (AUTO, MINI, SEDAN, SUV, PREMIER) with 5% GST and promo codes.
  The fare is base fare + per-km rate x distance (distance is straight-line x 1.3).
- **Matching:** open requests go to available drivers within 5 km. Drivers accept or decline, and a request
  nobody accepts expires after 10 minutes. Two drivers accepting at once is handled with optimistic locking.
- **Trip flow:** REQUESTED, ACCEPTED, ARRIVED, IN_PROGRESS, COMPLETED. The rider shares a 4-digit OTP to start the trip.
- **Real time (WebSocket):** ride status events, live driver location for the rider, and SOS alerts to admins.
  The WebSocket requires a token and restricts which channels each user can subscribe to.
- **Payments:** demo mode by default (no real money). The Stripe integration (PaymentIntent, signed webhook,
  idempotent handling) is in the code but is not exercised without a Stripe key.
- **Receipts:** PDF receipt generated by the backend after payment.
- **Ratings:** 1-5 stars per ride, driver average and a leaderboard.
- **Admin:** stats, users, drivers, rides, support tickets (SOS creates one) and promo codes.

## Environment variables (names only; never commit values)

### Backend (Render)

| Name | Required | Purpose |
|---|---|---|
| `CB_PASSWORD` | yes | Neon database password |
| `JWT_SECRET` | yes | Key used to sign login tokens (32+ characters, unique per project) |
| `CORS_ALLOWED_ORIGINS` | yes in production | Exact URL of the frontend, e.g. `https://cabflow-app-beta.vercel.app` (no trailing slash) |
| `PORT` | set by Render | Port the server listens on (defaults to 8080 locally) |
| `APP_ADMIN_EMAIL`, `APP_ADMIN_PASSWORD` | optional | Creates the first admin on startup if no admin exists. Change the password afterwards under Account. |

The database host and user are set in `backend/src/main/resources/application.yml` (they are not secrets).
Only the password comes from the environment.

### Frontend (Vercel)

| Name | Required | Purpose |
|---|---|---|
| `VITE_API_BASE_URL` | yes | Backend URL, e.g. `https://cabflow-app.onrender.com` (no trailing slash) |
| `VITE_CARTO_API_KEY` | optional | CARTO basemap key. Without it the map uses keyless Esri dark tiles. |

## Run it locally

Requirements: JDK 17+, Maven, Node 18+, and a PostgreSQL database (a free Neon project works).

**Backend**
```bash
# PowerShell:  $env:CB_PASSWORD = "<your-db-password>"; $env:JWT_SECRET = "<32+ character secret>"
# bash:        export CB_PASSWORD=...  JWT_SECRET=...
cd backend
mvn spring-boot:run          # http://localhost:8080/actuator/health
```
To use your own database, change `spring.datasource.url` and `username` in `application.yml`.
Tables are created automatically on first start (`ddl-auto: update`).

**Frontend**
```bash
cd frontend
npm install
npm run dev                  # http://localhost:3000
```
Locally the frontend talks to `http://localhost:8080` by default. Set `VITE_API_BASE_URL` in `frontend/.env` to point elsewhere.
The backend only allows the origin `http://localhost:3000` unless `CORS_ALLOWED_ORIGINS` is set.

**Tests**
```bash
cd backend && mvn verify     # unit tests + integration tests on an in-memory H2 database
```

## Deploy

1. **Database (Neon):** create a project (region Singapore). Copy the host and role into `application.yml`; keep the password for `CB_PASSWORD`.
2. **Backend (Render):** New > Web Service > connect the repo.
   Runtime **Docker**, root directory `backend`, health check path `/actuator/health`.
   Add `CB_PASSWORD`, `JWT_SECRET` and (after step 3) `CORS_ALLOWED_ORIGINS`.
3. **Frontend (Vercel):** import the repo, root directory `frontend`, add `VITE_API_BASE_URL` = the Render URL, deploy.
4. **Connect them:** set `CORS_ALLOWED_ORIGINS` on Render to the Vercel URL and redeploy the backend.
   If the browser console shows CORS errors, this value does not match the Vercel URL exactly.
5. **Verify:** open `/actuator/health` (should show `{"status":"UP"}`), then register a driver and a rider and run one ride.

## Try the whole flow

Use two browser windows (the second one private/incognito).
1. **Window A:** register as a **driver** (vehicle model and number), then press **GO ONLINE**. The location is a simulated GPS dropdown.
2. **Window B:** register as a **rider**, pick a cab tier and **Book**. Note the 4-digit OTP.
3. **Window A:** the request appears under *Ride Requests Nearby*. **Accept**, **Arrived**, enter the rider's OTP to **Start**, then **Complete**.
   The rider sees the cab move live while the trip is running.
4. **Window B:** pay (demo mode), rate the driver, and download the receipt.
5. Log in as an admin to see stats, drivers, tickets and promo codes.

The UI's places are Bangalore landmarks. Rider and driver must be within 5 km for a request to reach the driver;
both default to Indiranagar, so this works out of the box.

## API overview

| Who | Endpoints |
|---|---|
| Public | `POST /api/auth/register`, `POST /api/auth/login`, `GET /actuator/health` |
| Any user | `GET /api/users/me`, `PUT /api/users/me/password`, `GET /api/rides/active`, `GET /api/rides/history`, `GET /api/rides/{id}`, `GET /api/rides/{id}/receipt`, `GET /api/drivers/nearby`, `GET /api/drivers/top`, `POST/GET /api/support/tickets` |
| Rider | `POST /api/rides/estimate`, `POST /api/rides`, `POST /api/rides/{id}/cancel`, `POST /api/payments/rides/{id}/intent`, `POST /api/payments/rides/{id}/mock-confirm`, `POST /api/ratings` |
| Driver | `GET /api/drivers/me`, `PUT /api/drivers/me/status`, `PUT /api/drivers/me/location`, `GET /api/rides/available`, `POST /api/rides/{id}/accept|decline|arrived|start|complete` |
| Admin | `GET /api/admin/stats|users|drivers|rides|tickets`, `PATCH /api/admin/tickets/{id}/resolve`, `GET/POST /api/admin/promos`, `PATCH /api/admin/promos/{id}/toggle` |

List endpoints accept `?page=0&size=20&sort=field,desc`. WebSocket: `wss://<api-host>/ws` with the JWT in the STOMP `Authorization` header.
Subscribe to `/user/queue/rides` and `/user/queue/location`, send to `/app/driver.location` and `/app/sos`.

## Status and limitations

- **Deployed and working:** the backend runs on Render (Docker) and the frontend on Vercel. The full ride flow
  (booking, trip, payment, receipt) has been run end to end on the live site.
- **Payments are demo only.** Real Stripe card entry (Stripe.js) is not implemented, so no real money is processed.
- **Distance and ETA are estimates.** Distance is straight-line x 1.3 and ETA assumes 30 km/h; there is no road routing or live traffic.
- **Cab tier only affects price.** Any driver can accept any tier, because drivers do not have a vehicle category yet.
- **Receipt emails** are implemented but switched off (they need SMTP settings).
- **Login tokens are not revocable.** After a password change, existing tokens stay valid until they expire (60 minutes).
- **Not implemented:** Google OAuth, refresh tokens, chat or calls between rider and driver, driver payouts, Redis/Kafka.
- The in-memory WebSocket broker, rate limiter and cache work for a single backend instance only.
- `docker-compose.yml` files in the repo are from an earlier setup and do not match the current configuration.
  Production uses `backend/Dockerfile` on Render.
